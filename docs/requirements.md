# Keel — First-Principles Requirements & Engineering Principles

Design Philosophy bridges the human user's Core need to concrete design tradeoffs. Layer 1 defines the outcomes a rebuild must preserve. Layer 2 records how Keel delivers them with the current generation of executors.

## Design Philosophy

Keel exists for one developer or researcher delegating multi-hour engineering work to autonomous coding agents. Every mechanism in Keel follows five deliberate tradeoffs:

1. **User value over developer self-indulgence.** A repository's `## Core need` must describe who the human user is, what outcome they care about, and what real pain points hurt them—never feature inventories, framework boasting, or abstractions built for their own sake. When an agent loses sight of the user's need, it optimizes locally (clever refactors, cosmetic rewrites, or rigid boilerplate) while degrading the actual product. Keeping `## Core need` user-oriented and `## Design Philosophy` explicit in both root `AGENTS.md` (concise) and `docs/requirements.md` (detailed) gives every worker and verifier a shared compass.
2. **One thorough zero-context handoff over fragmented terse briefs.** Fresh subagent processes share zero chat history with the Orchestrator. Splitting context across a short CLI flag (`--why`) and an incomplete task file encourages duplicated, under-specified briefs where workers guess edge cases and verifiers fall back to generic boilerplate. Instead, `docs/tasks/{active,todo}/<YYYYMMDD>-<slug>.md` is the single authoritative handoff contract: thorough, self-contained, and proportional to slice complexity with no arbitrary sentence or line ceiling, while keeping lightweight `--why` + `--task` runs available for task-file-free branches.
3. **Root-cause verification with evidence-backed rebuttal over fake green or blind compliance.** An author who writes code and tests in the same session easily rationalizes symptom masking, weakened assertions, or unhandled edge cases. Independent clean-context verification in a disposable clone—exercising realistic caller workflows plus a one-line Canary mutation—catches fake green before it reaches `main`. Equally important, independent verifiers are not infallible: when a finding is a false positive or outside the locked bounds, authors and Orchestrators must push back with concrete technical evidence (captured under `## Decisions & Findings` -> `### Review Rebuttals`) rather than blindly contorting working code to appease a noisy review.
4. **Autonomous Orchestrator recovery before interrupting the human.** Human attention is the scarcest resource in an agentic workflow. Clear, reversible work should run end to end: match capability tiers to difficulty, diagnose rejections, step up capability on rework and re-verification, and stop at a bounded convergence cap. Interrupt the human only when judgment genuinely matters—direction-changing ambiguity, real product or architectural tradeoffs, unresolved convergence-cap blockers, or irreversible/external-blast-radius actions.
5. **Thin local-Git rebuildability over platform lock-in.** Agent CLIs, model lineups, and host plugins evolve every quarter. By keeping timeless user outcomes (`Layer 1`) separate from thin Python 3 stdlib glue, local Git state, and public CLI/hook contracts, Keel stays inspectable, offline-capable, and cheap to adapt or rebuild without tying a repository to hosted PR APIs, proprietary ticket trackers, or undocumented internals.

## Layer 1: Pure Requirements (Timeless Human & Outcome Needs)

### Core Must-Haves (`R1`–`R5`)

1. **`R1` — Preserve native model capability.** Match reasoning capability and effort to the difficulty of the slice. A difficult change must have access to the model's full native capability. Underpowered assignments cost rework rounds, while maximum effort on routine tasks wastes time and capacity. Keep process instructions and tool restrictions light enough for the selected model to exercise its own judgment.

2. **`R2` — Preserve the project's Core need across contexts.** Both implementers and independent verifiers receive the project's user-oriented `## Core need`, `## Design Philosophy`, the slice's purpose (sourced directly from the task specification's `## Goal & Why` / `## Why` when present, or explicit Orchestrator `--why`), and its `main`-locked goal, bounds, and done criteria when a task specification exists. This context must survive compaction and workspace isolation. Exclude the author's chat and private reasoning from verification while preserving the project purpose, locked task bounds, and clearly labeled advisory author context (`Progress`, `Decisions & Findings`, `Review Rebuttals`). Every agent should flag a local fix that would undermine the global goal.

3. **`R3` — Deliver root-cause fixes that withstand independent verification without review deadlocks.** Before integration, require passing deterministic checks and an independent, clean-context review that exercises realistic caller workflows against the Core need and agreed task bounds. Verify that the checks detect a meaningful break. Masking symptoms, weakening valid assertions, swallowing errors, silently degrading behavior, or patching private third-party internals to force a pass requires correction. Avoid contrived OS or kernel fault injections outside the slice's realistic fault model. On rejection, the Orchestrator checks the finding against the caller's workflow and task criteria, diagnoses the root cause, then directs a fix for a confirmed defect or records structured technical pushback (`keel branch dispute` or `### Review Rebuttals`) without forcing regressions onto clean code. Subsequent review rounds re-adjudicate prior `blocking` items against commit deltas and author rebuttals while keeping the full `merge_base..HEAD` diff open for genuine missed defects. Bound review rounds and resolve rebuttal stalemates or convergence-cap deadlocks through an impartial top-tier Arbiter (`approve`, `rework_once`, `replan`, `pivot`, or `park`) with bounded structural recoveries before interrupting the human.

4. **`R4` — Protect scarce human attention.** Clear, reversible tasks proceed end to end without prompt restatement or repeated permission gates. Interrupt the human for direction-changing ambiguity, genuine product or architectural tradeoffs, or irreversible actions and actions with external impact. Present viable tradeoffs neutrally and give the recommendation last. Landing, releasing, deploying, discarding unintegrated work, force-pushing shared refs, and mutating external state require explicit authorization unless standing delegation covers the action and target.

5. **`R5` — Support task-matched dispatch across pluggable executors.** Route research, prototype comparisons, debugging, implementation, and verification to a capable model on any suitable executor (`1..N`). Match each assignment to the slice's actual difficulty as models and runtimes evolve. Concurrent writers need isolated workspaces, and every dispatched agent needs the project and task context required for its assignment.

### Detailed Needs (`D1`–`D3`)

- **`D1` — Size the work proportionally.** Reserve direct main-session edits for trivial, few-line changes where writing a brief outweighs the edit; dispatch substantive single-slice work to a clean-context writer matched to the slice's difficulty. Before dispatching a multi-module overhaul, divide it into small, sequential slices with independently checkable outcomes. Existing repositories, branches without task files, and offline or SSH-remote workflows must work without mandatory ticket templates, hosted pull requests, or custom CI job names.
- **`D2` — Keep casual chat free of workflow overhead.** Non-engineering conversations incur near-zero token overhead and zero workflow prompts.
- **`D3` — Keep the harness thin and rebuildable.** Separate durable requirements, configuration, and execution glue by responsibility so each can be changed or rebuilt independently. Maintaining the glue must never eclipse the project work it supports.

### Explicit Outcome Red Lines (`NR1`–`NR4`)

- **`NR1` — No process bureaucracy.** Avoid ceremonial templates, permission gates on clear reversible tasks, and multi-agent committees on atomic edits. Judge simplicity by how clearly responsibilities are divided, and avoid arbitrary upfront line-count quotas or edits made solely to hit a line count.
- **`NR2` — No false-positive developer friction.** Guards must block unauthorized default-branch changes and destructive force-pushes while allowing routine operations such as tests, filenames like `src/merge.py`, `git pull --ff-only`, and normal `main` pushes.
- **`NR3` — No repo pollution or platform lock-in.** Keep scratch handoff files and verification state out of version control. Local branch workflows must work independently of hosted platform APIs.
- **`NR4` — No brittle couplings.** Use public host contracts and structured configuration. Never parse prose tables as configuration or scrape undocumented host directories.

## Layer 2: Late-2026 Frontier Engineering Principles (`P1`–`P5`)

1. **`P1` — Keep the daily Orchestrator loop resident.** In `rules/AGENTS.md`, §§1–3 apply to every agent. Section 4 supplies the daily Orchestrator loop for the main session only. Of these sections, `context.py` injects only §§1–3 into worker briefs delivered by file or stdin. Keep infrequent procedures in a single on-demand `keel-repo-ops` skill. Each project's root `AGENTS.md` is a concise six-section map (`Core need`, `Design Philosophy`, `Architecture & Boundaries`, `Commands`, `Gotchas`, `Where to look`), paired with a detailed `## Design Philosophy` in `docs/requirements.md` (or `docs/prd.md`). Select entries by their value to someone working in the repo, without a fixed line ceiling.

2. **`P2` — Make `docs/tasks/` the single `main`-anchored zero-context handoff contract.** Open non-trivial tasks in `docs/tasks/{todo,active,archive}/<YYYYMMDD>-<slug>.md` on `main` before branching, written thoroughly enough for a fresh zero-context worker or verifier (no sentence or line ceiling). When `--task-file` supplies a non-empty `## Goal & Why` (or `## Why`) section, `--why` is optional on both `keel agent run` and `keel branch verify`; supplementary rework or pivot notes can travel via `--context-file` without mutating the `main`-locked spec. The `main` versions of `Goal & Why`, `Bounds`, and `Done-check` are immutable for the slice. Workers may update `Progress` and `Decisions & Findings` (including `### Review Rebuttals` for evidence-backed pushback against disputed review findings) on the branch, which `keel branch verify` surfaces as advisory context alongside `main`'s authoritative locked specification.

3. **`P3` — Configure model levels once and dispatch synchronously.** Define the L1–L4 capability ladder and each executor's model and effort mapping in `config/defaults.json`. Choose a level for the slice independently of executor, read/write mode, and context preset. Run both `codex` and `agy -p` synchronously and collect the result on exit. Omit `--new-project` from `agy -p` so headless runs reuse the CLI Project without adding projects to the UI sidebar. Isolate concurrent writers in task worktrees and supply the project and task context even when an executor starts in a disposable clone.

4. **`P4` — Verify independently at the implementation level with Carry-Forward memory and bounded 5-action Arbitration.** Default to a same-level cross-vendor diagonal. An `agy` implementation at a given level goes to a `codex` verifier at that level, and a `codex` implementation goes to `agy` at the same level. In a clean disposable clone, verify the locked criteria through realistic caller workflows proportional to the change. Make a one-line Canary mutation, confirm the relevant check fails, and restore the clone. Validate the verdict against `config/schemas/verdict.schema.json`, keeping must-fix findings in `blocking` and optional findings in `notes`. On Round 2+ of an active review cycle, inject a structured Carry-Forward ledger (prior `blocking` items, commit delta, and `keel branch dispute` rebuttals, never writer chat logs) while keeping full `merge_base..HEAD` inspection unblinded; on `--dual` Round 2+, pass the Carry-Forward ledger only to the primary cross-vendor verifier so the second verifier stays clean-slate blind. After a rejection, step up the model level for both rework and subsequent verification up to `L4`, bounded by the tier-aware convergence cap (`L2(1) -> L3(1) -> L4(2)`). On a rebuttal stalemate or convergence cap, `keel branch arbitrate` runs an impartial `L4` Arbiter (`config/schemas/arbiter.schema.json`) in a disposable clone to choose `approve` (waiving non-blocking/false-positive items with `Keel-Arbitrated:` provenance), `rework_once` (one single-use bonus `L4` round), `replan` or `pivot` (retiring the branch safely via `keel branch supersede`, preserving `refs/keel/superseded/<slug>/...`, and propagating dead-end lineage up to `max_structural_recoveries = 2`), or `park` (halting for genuine human decisions or exhausted recoveries). Carry verification—including `arbiter-approve`—across a pure rebase only when the rebased Git tree SHA matches the expected tree from applying the verified change to the new base.

5. **`P5` — Keep the branch gate local and flat.** Store each branch's verification and landing state in `<git_common_dir>/keel-state/branches/`. The gate records the synchronous verifier result directly, without asynchronous pending-verifier claim tables or a manual record-verdict step. Bundle task archival into the atomic squash land. Keep `PreToolUse` guards slim by checking parsed command segments for prohibited operations, so legitimate commands and filenames pass.
